# Owner inventory assessment for exact CompanyRecords

## Authorized boundary

The owner authorized one Outcome 0 step in the existing **To organize** catalog: inspect one exact CompanyRecord and its source, preview the effect, then record an owner assessment of its purpose as business, test, audit or explicitly unknown with a reason. Corrections retain history. A change to the canonical record makes the last assessment stale until the owner reassesses it. This classification is an owner assertion about inventory purpose, not verification of source truth or approval for task/agent context.

The gate permits an additive database migration, scoped API and owner UI, native disposable PostgreSQL/API and PL/EN browser tests, independent UX and Security review, a scoped push and at most one standard Coolify deployment after fresh backup, isolated restore, capacity and rollback checks. Production smoke is read-only. It does not authorize classification of any real production record, record deletion/archival, bulk decisions, model/Worker calls, changes to task-source admission or a later gate. The estimate is 12–20 technical hours without a fixed implementation timer; at most two materially changed repair attempts.

## Starting evidence and contract

The deployed `c83a10f2` source catalog groups exact saved metadata and retains flat search, Current/History, exact detail and task-bound source audit. Existing `CompanySourceReview` entries classify fact/observation/proposal/inference for one task and can approve context only through separate guards. They are not inventory-purpose assessments. The documentation importer updates existing CompanyRecords, including their metadata and `updatedAt`; a purpose assessment must be outside that body and bound to its exact version. The postrelease documentation evidence from the prior gate was selectively carried forward as local commit `a51cfb01`, without a separate release.

The implementation keeps one append-only assessment chain per workspace and canonical record ID. Each row records a full-record version/digest, actor, category, reason, source reference, predecessor and idempotency key. The owner-only `GET /v1/company-records/:id/inventory-assessments` returns the exact current body, saved provenance, assessment state and paged correction history. `POST` requires the expected version, digest and latest assessment ID, a category and nonblank reason; a repeated identical request is idempotent. The database rejects updates and deletes to assessment rows and forks in the correction chain. A canonical record row lock serializes assessment with edits and organizational-context assignment. The read model distinguishes no assessment, an explicit unknown assessment and a stale assessment. It never changes verification state, source reviews, agent admission, status, scope or content.

In the owner console, each original record shows its assessment state and opens a one-record modal. The modal loads the exact current body and source, then requires category and reason before a separate effect preview and save. It shows corrections and their saved provenance, localizes refusal/recovery text in PL/EN, and on uncertain network outcome keeps the request immutable until the same request is retried or a fresh read reconciles it. A changed record loses the current category badge until reassessed; the prior assertion remains in history. No group, document or bulk classification action exists.
