## Local implementation and evidence checkpoint

`GET /v1/company-records/registry` adds a human, workspace-scoped compact projection. The legacy `GET /v1/company-records` array is unchanged for existing clients. The new route enforces a maximum 100 rows, returns no record body or review content, caps source display fields, and uses deterministic `updatedAt, id` ordering inside a repeatable-read count/page transaction. It retains active unverified records in Current; History selects `archived` explicitly. The owner-only source audit remains a separate exact-record, task-bound read. Existing signed-in member and viewer register reads remain available; task-scoped humans and agent keys are denied by existing middleware.

The focused G9a native HTTP/MCP suite passed 8/8 against an owned disposable PostgreSQL database after all migrations. Its added case inserted 5,231 CompanyRecords with company scope, then exercised bounded pages, search, current/history, omitted body fields, oversized source metadata, workspace and role separation, and legacy response compatibility. The harness removed the disposable database and role. This is local/native evidence, not production UI proof.

The focused browser script passed six PL/EN owner/member, 390/1280-pixel scenarios. It exercised server paging and search, Current/History, archived read-only detail, exact Source navigation for the owner, member list access without source audit, empty/error and retry states, delayed-response races, keyboard navigation and absence of business writes. The independent UX review reran those cases and visually checked 50 cards at 390 pixels: the top pager remained reachable before the list and no horizontal clipping occurred. It found only an empty, roughly 35-pixel table toolbar band. The independent Security review found no concrete authority or information-exposure issue after the human-read parity fix; its feedback led to a bounded source-metadata projection. These reviews and tests do not establish a signed-in production walkthrough.

Root reran the final native 8/8 and browser 6/6 checks after integration. `npm run validate` passed lint, typecheck and server/web build. `npm run codex:check` passed preflight, 236/236 requirement traceability rows and three infrastructure checks. The new route has no schema migration. The existing legacy array endpoint remains for other callers, and `contextualEntityIds` still assembles the contextual ID set before querying a page; neither is evidence that every CompanyRecord consumer is bounded.

Read-only release preflight: remote `main` and public API/web health both reported `c7f375dd8b948597552ba669af4215055a01c7ff`; the running backend used that exact retained image. The PostgreSQL container was healthy on its named persistent volume, 158 migrations were finished with none unfinished, and the prior backend image remained available for code rollback. The VPS had about 12.8 GB free. Production held 5,231 CompanyRecords (2,403 active, 2,828 archived) and two source reviews before release. The older backup/isolated-restore proof was not refreshed because this slice has no schema or production business-data write.
