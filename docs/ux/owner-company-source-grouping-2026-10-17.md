# Owner source grouping for unassigned CompanyRecords

## Approved boundary

The owner approved one bounded follow-up to the deployed **To organize** catalog. Group the 2,400 current documentation-import fragments by the exact recorded workspace, application, source system, source root and source revision; within a group, list source documents by exact recorded file path, then the original records. Keep the three other current records separate from documentation imports. Preserve the existing flat server search, Current/History, pagination, exact read-only detail, and task-bound source audit. Correct the History introduction. No record approval, classification as disposable, data write, schema migration, importer change, Worker/model call, or next gate is authorized.

Allowed delivery effects: Roost API/web code, tests and canonical documentation; one scoped push and at most one standard Coolify deployment after backup, restore, capacity and rollback preflight. Signed-in production verification is read-only. VPS cleanup is limited to previously authorized unused builder cache; any other cleanup or capacity change needs a separate decision.

## Entry evidence and design

The existing owner catalog was deployed on build `72d70418`. Read-only production metadata aggregates found 2,400 non-archived documentation-import records in five exact source groups and 133 source documents. All 2,400 have an application link and the required source fields are recorded as strings; 842 explicitly say `legacy_assumption`, while 1,558 have no `sourceKind`. Three other current records are outside documentation import. These counts describe recorded metadata, not an independently verified import event, canonical authority or task approval. No record body was read for this classification.

`GET /v1/company-records/registry/unassigned` now accepts `level=groups|documents|records`, with opaque `groupId` and `documentId` selectors. The old flat records response remains the default for existing callers. All levels retain owner-only workspace authorization, Current/History predicates and literal server search. Group and document counts/pages are read under repeatable-read transactions. Complete documentation provenance uses exactly the recorded application, sourceSystem, sourceRoot, sourceRevision and filePath; missing or malformed required values go to a separate incomplete group. Non-import records appear as individual other entries, identified by their original record key. A missing or whitespace `sourceKind` stays unspecified. The response does not infer source trust or change eligibility.

The owner view starts with source groups. An import group opens documents, then original fragments; incomplete and other groups open their original records directly. Application IDs distinguish names that collide. Search switches to the existing flat result list. Breadcrumbs, back controls, keyboard buttons, counts, PL/EN labels, source-kind gaps, exact detail and source audit remain available at 390 and 1440 CSS pixels. The History text describes archived records accurately.

## Verification and release

- Native disposable PostgreSQL/API proof passed 10/10 after all migrations. It covers exact cross-application and revision grouping, document/fragment pages, two non-import records without application links remaining distinct, malformed provenance isolation, blank/missing `sourceKind`, flat search, History, workspace isolation and owner/member/agent/anonymous boundaries. The owned test database and role were removed; the prior local container state was restored.
- The owner browser fixture passed 4/4 PL/EN journeys at 390/1440 CSS pixels, including keyboard group/document/record navigation, a non-import singleton, two applications with the same name, leaf pagination, exact detail and source audit in Current and History, flat search, retry and member refusal. `npm run validate`, `npm run codex:check` and `git diff --check` passed. The browser fixture does not itself exercise page two of a 26-group or 26-document list; native API tests exercise group/document pagination.
- Independent Security and UX code reviews found the initial non-import group key could merge records from different applications, whitespace `sourceKind` counts could disagree with the leaf label, and app-name-only rows could be ambiguous. The final code uses one non-import group per record, normalizes blank kind and shows stable application IDs. The exact-detail label now describes the absent department/company scope. Both reviewers re-read the final diff and found no further concrete blocker; their reviews were static, while the root owner ran the native and browser tests above.

Read-only release preflight still showed the previously deployed `72d70418`, finished Coolify queue `6453`, healthy retained PostgreSQL and 10,596,810,752 B free on the VPS. The documented build planning allowance is 12,884,901,888 B. Docker reported 1.978 GB of private reclaimable builder cache. The one standing-authorized `docker builder prune -f` removed exactly 1.978 GB of unused cache; a fresh physical `df -B1 /` measured 12,574,363,648 B free, still **310,538,240 B below** the allowance. Build cache reclaimable is now 0 B, and both backend and PostgreSQL stayed healthy. No image, container, volume or business record was removed or changed. This gate stopped before backup, push and deployment. No signed-in production source-grouping proof is claimed.

Recovery proposal: add VPS capacity with enough measured margin above the allowance, or separately authorize one exact unreferenced older backend image after confirming it is not a protected rollback artifact. Current and immediately previous backend images must remain. The image path would need a fresh ID/reference check and physical space read-back before backup or release. This proposal is not authorization for either effect.

The approved cap is one production deployment. G24c/G25 and broader RF-CTX-027/RF-UX-010/RF-UX-012 acceptance remain open beyond this bounded navigation slice.
