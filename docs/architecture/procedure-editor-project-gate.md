# Exact-project Procedure editor and owner activation review

## Authorized boundary

This one RF-CTX-026/029, RF-ORG-002 and RF-UX-012 gate lets the owner prepare a complete one- or two-step manual Procedure for one exact active Project, review its saved version, and obtain a truthful launch preview. The authorized release includes API and PL/EN owner UI changes, native PostgreSQL and responsive browser tests, independent Security and UX review, one normal deployment after preflight, and read-only production smoke. It does not authorize a production Procedure create, activation, launch, ProcedureRun, Task, Worker, model, provider, or external task write. The first production definition and run require separate exact owner decisions.

## Contract

- The editor exposes structural applicability (exact Project or company), accountable role, step executor, input field names, output description, success rule, attempt limit, and fallback. Editing a saved structured output description preserves its other keys. Existing drafts can be saved; editing an active version creates a separate draft revision.
- A Procedure with project applicability must reference an active Project in the same workspace. The generic organizational-context PATCH cannot alter a Procedure scope outside its versioned route. Draft PATCH compares both draft status and revision timestamp before replacing steps or context, so a concurrent activation cannot be overwritten in place.
- Activation requires the workspace owner and the exact version and timestamp shown in its separate review. It rejects an incomplete exact-project definition with named blockers. Serializable activation keeps at most one active version in a family; status, audit, and event commit together. A same-family concurrent loser receives a conflict. The final human owner role may have no fictional escalation target only when it is explicitly a human role with both `workspace:admin` and `approval:decide`; unresolved exceptions stop at that owner decision.
- Activation only makes a version available for launch preview. The existing owner-only launch path still requires a fresh exact-project preview and separate confirmation before it can create Roost-native Tasks. It rechecks project and role state at launch.

The existing product-engineering versioning test passed with the reviewed activation request. The styled owner editor test passed four PL/EN journeys at 390 and 1440 CSS pixels: a two-step draft, preservation of structured output, exact Project and role, activation review and Escape, translated incomplete-definition feedback, and activation without launch. `npm run validate`, `npm run codex:check` and `git diff --check` passed. Independent Security and UX reviews initially found concurrency and feedback defects; their focused re-reviews found no remaining release blocker after repair.

These tests use fictional data and an isolated local database. They do not prove a real production Procedure definition, activation, launch or completed Task. Project/role state can change after activation readiness checks; the launch path rechecks and remains blocked for stale state. Release and signed-in production smoke evidence will be recorded separately after deployment.
