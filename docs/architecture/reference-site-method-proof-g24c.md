# G24c task-bound method mechanism

## Authorized boundary

The owner authorized a bounded G24c mechanism: an approved reference-site checklist may be selected for one assigned company-information runtime task, bound to Ready, and carried into one sealed, no-tool Hermes input. This slice does not create a real production Site, Finding, checklist, task, model call, application change or supervised result. A real G24c method proof still needs an exact owner decision on its content, task and model budget. G25 is outside this scope.

## Runtime contract

The owner Ready editor obtains the newest checklist decision for the current task independently of the generic 50-Procedure catalog. It reports none, current, stale or withdrawn, shows the decision and version, and permits at most the current version to be selected. A stale selection can be removed or replaced explicitly. Other Procedures remain separate. The editor never offers another task's checklist.

On Ready resolution, the server admits the selected checklist only for the assigned agent and company-information runtime class. It rechecks the active Procedure and exact decision receipt, each approved site and task source review, current record revision, approved Finding version and independent review, package/metadata digests, observation evidence and equality of the configured site URL with the package's published URL. The selected site must also be selected as company context. A mismatch invalidates Ready before admission. These reads participate in the existing Ready source-watch revision; immutable receipts and Finding versions are read by exact ID.

The resulting bounded projection has one or two items, exact Procedure family/version/decision, item IDs, source IDs and revisions, and the saved observation with its evidence scope. It is in the execution packet and therefore its digest and Ready revision bind the signed managed admission and sealed Worker input. Worker validation rejects foreign task/agent/source, unselected or changed Procedure, changed review, duplicate Finding and inconsistent evidence kind/scope. The runtime remains one turn, no tools, no native authority and no external writes; its instruction distinguishes saved source evidence from supervised results and forbids claiming a fresh site visit. The existing owner result review remains the acceptance boundary.

The server checks current source and Ready when signing managed admission. The signed grant lasts at most 45 seconds; the local launcher verifies that grant and its sealed snapshot, but does not fetch source state again immediately before Hermes starts. A change in that narrow interval can make the source stale after admission. This is a temporal limit of the existing managed runtime, not atomic proof that every source stayed current through process start. A supervised owner review must inspect the result and this limit before accepting real proof.

## Later bounded live Finding session (stopped before tools)

The owner later approved one separate local Hermes/MCP session for an assigned information Task and two exact, task-approved saved Site revisions. The intended effect is at most one owner-reviewed Finding creation for each of two pinned observations. This is a preparatory Finding step, not the checklist adoption or supervised method proof above. It uses a separate Hermes profile rather than the managed no-tool Worker profile. A single local model attempt, up to 600 seconds and one turn, has its own owner budget; there is no paid fallback or automatic retry.

The opt-in local STDIO bridge guard requires a private configuration outside this repository with the exact Task ID, two Site/observation pairs, source review IDs, Site revisions, package digests, expiry and private slot directory. The actual session launcher must pass `--require-finding-guard`, which fails if the configuration is missing. The guarded MCP catalog contains only the package GET and Finding POST. Every call is checked against the Task and Site; a Finding body must match the configured observation, current review, revision and package digest. The full destination URL and exact JSON body are displayed to the owner on a loopback page before each POST; the owner confirms the request digest. The bridge reserves a per-pair slot with exclusive creation and file sync before sending, does not follow redirects, and treats transport loss or redirect as a spent, uncertain attempt. The backend additionally uses a stable per-pair request ID so an accidental repeat after a host crash is a replay or conflict, not a second Finding record.

The slot survives an ordinary bridge process restart. Directory-entry survival after sudden power loss is unproven on this Windows host, so a literal one-wire-POST guarantee across power loss is not claimed. Another process running as the same Windows user could inspect or approve the loopback page; this remains within the accepted same-account host risk only if the Hermes model has no terminal, browser, HTTP or other local-process tool. Inspect the actual tool inventory and profile before the attempt. The local approval page is not a Roost owner-authentication receipt. Company data and the agent key belong only in private session state, never this document or the repository.
