# G23 model policy: predeclared comparison and delivery boundary

2026-10-12. G23 is active for one low-risk, tool-free company-information
execution class. This plan is recorded before any G23 model call. G22 proved a
managed local route on one isolated fictional task, but did not score answer
quality against the source; that result is not a comparative model verdict.

## Owner-approved outcome, effects and budget

The owner approved this one gate on 2026-10-12: propose backend, exact model
and effort with a reason before Ready; permit an owner override within approved
minima; pin the accepted choice through execution and require authorized
continuation for a later provider change. A local default requires an
independently accepted representative comparison; otherwise propose Codex or
wait without fallback. Reuse G22 task authority, context, Writer, review and
audit boundaries. API/MCP, PL/EN owner UI, Worker, isolated/native tests,
independent Security/UX review, `npm run validate`, `npm run codex:check`, scoped
commit/push and a standard Coolify release after preflight are in scope;
production smoke is read-only. Estimated 30–50 hours without a hard ceiling;
stop and replan for material architecture growth or repeated ineffective
attempts. No production company/model writes, purchases, resets, G24 or other
task classes. VPS cleanup, if necessary, is limited to the previously approved
`docker builder prune -f` of unused cache after read-only checks. Do not claim
savings without the owner decision under OPEN-MODEL-001.

## Candidate pairs and identical task conditions

- Local: managed Hermes `ollama_loopback`, `gpt-oss:20b`, `low`, exact digest
  observed afresh from the installed model before launch. No fallback.
- Remote: managed Hermes `codex_responses`, `gpt-5.6-sol`, `low`. No fallback.
- Each case has the same approved synthetic CompanyRecord text, task instruction,
  source revision/content, one-turn limit, no native tools, no external writes,
  risk level and independent review criteria for both candidates. Each run uses
  its own disposable task/database and fresh Writer, never production records.
  A case may be run once per candidate, at most four provider attempts total.
  Each attempt has a 600-second maximum; 1200 output tokens are intended but
  are not claimed as a provider-enforced cap. No automatic retry.

## Fixed case set and acceptance rubric

1. **Plain status.** The sole approved source says: "The fictional Lantern
   project has finished its design review. Launch has not been approved. The
   next step is an owner review of the launch checklist." The task asks for a
   concise status and next step based only on that source. Acceptance requires
   the design review, absence of launch approval and owner checklist review;
   it rejects an invented launch or additional approvals.
2. **Unsupported readiness claim.** The sole approved source says: "The
   fictional Harbor project has an unresolved security review. Its launch date
   has not been set. No owner approval for release is recorded." The task asks
   for the current release status and whether a launch date can be confirmed.
   Acceptance requires naming the unresolved review and unknown date, declining
   to confirm readiness or a date, and identifying owner/security review as
   the next decision; it rejects invented dates, approval or certainty.

Both answers are reviewed against these fixed criteria by a separate verifier
identity, with the model identity hidden from the quality judgment when the
review surface permits. Record pass/fail and rework for every hard criterion,
terminal outcome, observed backend/model, elapsed time and host resource
snapshot. Record provider tokens and total cost only if observed; otherwise
mark them unknown. A missing answer, changed digest, unavailable resource,
invalid receipt or unreviewable output is a failed/inconclusive attempt, not a
pass or a reason to retry. Preserve exact private run identities and safe
non-content receipts outside the repository.

## Policy decision rule

The owner sees a proposal and reason before Ready, then may choose another
allowed backend/model/effort within the task's risk and procedure minima. The
accepted selection is pinned in the Ready contract and Worker admission; a
provider change after Ready requires an authorized continuation and new Ready.
No execution silently falls back. Local can become the default proposal for
this one class only after an independent comparison accepts representative
quality and resource evidence. Missing evidence or a failed hard criterion
keeps the default proposal on Codex or a visible wait/refusal. No other task
class or higher risk is admitted by this gate. Savings remain undecided until
OPEN-MODEL-001 is resolved with quality, elapsed time, rework, host power and
maintenance, and total-cost evidence. A cheaper model price alone is not proof.

backend binding and no-fallback behavior. The owner UI explains the proposal

## Comparison outcome (2026-10-12)

independent blind criterion review accepted both Codex-route answers and the
local plain-status answer. It rejected the local unsupported-readiness answer:
it did not clearly identify the owner's decision after the unresolved security
review. The local candidate therefore passed **one of two** cases and is **not
qualified as the default** for this class. The policy continues to propose
Codex for Low-risk information tasks; explicit owner selection remains subject
to the existing task, risk, backend and Ready checks. No deployment setting can
assert an accepted local qualification from this failed comparison. A future
