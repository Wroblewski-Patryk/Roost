# G18a — ClickUp status authority for one selected List

## Owner-approved boundary

One explicit `governedStatusListId` from the ClickUp integration's existing `listIds` opts a workspace into G18a. With no selection, existing behavior remains. The selected List uses ClickUp as the only task-status authority. Roost retains authority for goals, decisions, accountability, Ready, review, permissions and its organizational links. No real ClickUp task is changed for G18a verification; production smoke is read-only. G18b is outside this gate.

The ClickUp Update Task API documents an unconditional `PUT` without a version or `If-Match` precondition. A provider read immediately before that write cannot protect a simultaneous ClickUp user change or List move. While governance is configured, Roost therefore stops direct status PUT, archive, task moves, and legacy manual sync across the entire workspace ClickUp integration. Direct creation in the selected List is also blocked; creation in other Lists and non-status field edits remain available. This workspace-wide restriction was separately approved by the owner after Security review. A Roost status command for the selected List writes an auditable intent, then posts a request comment containing the intent ID. It never presents that request as a completed status change. A response lost after POST remains `uncertain`; Roost does not automatically send the comment again.

## Authority and recovery contract

| Field or action | Authority | Roost behavior |
| --- | --- | --- |
| Task status in selected List | ClickUp | Apply only a signed, in-scope status webhook followed by a fresh provider task read. Initial import may establish a new task's baseline. Later imports show provider status but preserve the canonical status until a signed event. |
| Status request from Roost | Authenticated human | Persist one open intent per task, append one ClickUp comment, verify its ID/text by provider readback, show `posting`, `awaiting_provider`, `uncertain`, `confirmed`, `conflict`, or `closed`. |
| Title, description, priority, due date | Existing ClickUp two-way mapping | Existing provider mapping continues for these fields. |
| Goal, owner, assignee, Ready, review, decisions, permissions | Roost | Provider events cannot modify these fields. |
| Provider actor | ClickUp event | Persist provider user ID and label `unverified` until an explicit identity binding is available. Never infer a Roost person from a name or email. |

The signature uses the registered webhook secret. Ingestion rejects inactive or deselected registrations. Processing checks that the provider task belongs to the registration's List before creating or updating a canonical task. Inbox idempotency and the workspace integration lock prevent replay of each provider event. A signed status event with status history changes the canonical status only when its `after` status matches a fresh provider readback; if the readback has advanced, Roost records a visible conflict without assigning the older event's actor to the newer status. A signed move without status history updates List membership but does not borrow the current provider status as status-event evidence. An importer that sees a task leave the selected List before the signed move preserves local List and status, showing a conflict. Out-of-scope events are retained as `rejected` without automatic retry; provider outages remain `failed` for bounded maintenance retry. A deletion event without a successful task read cannot change status for the governed List.

The selected List requires an active webhook before a status request. A version mismatch between Roost and provider is recorded as `conflict` without posting a comment. Only an owner may close a conflict or uncertain intent; closing audits the decision and permits a new deliberate request. Closing does not assert that an uncertain ClickUp comment was absent.

ClickUp offers no conditional comment POST against List membership. The owner accepted the remaining possibility that a task is moved just before comment creation. Roost reads membership before and after POST, records a persistent conflict when it detects the move, and never automatically repeats the comment. This detects the race after the fact; it cannot guarantee where ClickUp placed the comment at the instant of POST.

## Acceptance and evidence

RF-PROD-003 and RF-INT-001–005 define identity, one field owner, provenance, conflicts and recovery. RF-SEC-001–007 govern least authority, redaction and review. Local proof must run additive migrations on disposable PostgreSQL with an isolated ClickUp HTTP fixture and test the complete intent/comment/readback/signed webhook/reconciliation path. Negative cases include invalid signature, deselected or other List, duplicate/replay, provider outage, uncertain POST, local/provider status mismatch, and preservation of Roost-owned fields. `npm run codex:check`, component tests, frontend build, independent Security review and production read-only smoke are required before claiming the gate delivered.
