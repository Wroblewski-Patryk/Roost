# G18b — task-bound Google Doc

## Accepted boundary

The owner authorized one Google Doc journey inside an already selected Drive folder: one task and owner-approved source, current read, one revision-conditional edit, durable intent, provider readback, and visible conflict or uncertain state across PL/EN owner console and the scoped API/MCP surface. The existing Google adapter is reused. Isolated PostgreSQL and a Google HTTP fixture provide write proof; production smoke only reads and does not edit a real Doc. No G19, paid model, purchases, resets, VPS cleanup, synthetic production records, or production Google edits are in this gate. Estimate: 20–35 hours of work without a hard cap; one implementation attempt, with ordinary repairs. A material architecture expansion or repeated ineffective attempts stops the gate.

The owner separately accepted the unavoidable folder-move race. Docs `batchUpdate.requiredRevisionId` rejects a stale document revision, but it has no predicate on Drive parents. Roost reads the provider's current metadata and selected-folder ancestry immediately before and after the write. If the file leaves the folder between those checks, the write may have occurred outside the selected scope; Roost records a durable conflict and does not retry automatically. The owner must inspect the Google result.

The same cross-system boundary applies to local authority: a task completion, reassignment, key revocation or source withdrawal can land after Roost's last pre-send check but before the Google POST. Roost checks authority again after provider readback and records a conflict, but it cannot prevent or undo an already accepted Google write in that narrow interval. This residual risk is disclosed for owner review before release; the previously accepted folder-move exception does not by itself approve an authority-change exception.

## Authority and state contract

- Drive owns file location and content; Roost owns task context, owner source approval, the one-edit mandate, intent and audit. Google actor identity is unverified unless provider evidence explicitly verifies it. File identity uses the immutable Google ID, never a name.
- The mandate binds workspace, task, file, selected folder, latest approved source snapshot, assigned agent, its exact credential/version, expiry and owner. It can be issued and used only while the task is `todo` or `in_progress`; a database trigger permanently revokes it when the task becomes done, blocked or archived, or its assignee changes. A later return to the old state cannot revive it. Human access uses an authenticated workspace owner. The owner confirms the exact mandate with a fresh password proof; the review records an owner attestation, not a claim that the API observed a human reading the Doc. Generic Drive routes cannot mutate a mandated Doc or return its content through an unbound agent key.
- A current read queries Drive metadata and Docs content. It refuses a file outside the configured folder, a changed or withdrawn source review, or an unavailable provider. The Docs `revisionId`, not Drive `headRevisionId`, is the content version for a Google Doc. Drive only exposes `headRevisionId` for binary content.
- The bounded edit appends owner/agent-supplied plain text to the first document tab. It never replaces the original rich content. A unique request ID and a single durable intent are committed before `batchUpdate` with `requiredRevisionId`; all ambiguous send/readback failures remain uncertain, and a stale revision or moved file is a conflict. There is no automatic resend. The result records provider revision and a readback of the same file. Roost checks its own mandate/source authority again after the provider response and records a conflict if that authority changed during the write. Closing conflict or uncertain state needs an explicit owner action, without replaying the edit. A `posting` request is never closed solely because 90 seconds elapsed: it may still finish later, so the view flags a possible late write and keeps closure disabled.
- Stored source snapshots and intent history remain separate from Google's authoritative original. A provider change invalidates the old approval for future edits. The exact actor may read its confirmed result only while the latest source review still authorizes the original approved snapshot and the mandate is live; a withdrawal denies that read. A single mandate and intent are retained per task and file in this bounded gate. Further editing needs a separately authorized design and cannot silently recycle the mandate. Owner console shows both provider state and the intent; MCP advertises only task-bound tools to agent principals.
