# Trusted company information packet v1

G8 applies to the tool-free company-information task path. A company record's editable `status`, `verificationState`, `source`, and `metadata` do not constitute source approval. Existing records have no implied approval.

An owner may append a `company_source_reviews` receipt for one task and one exact company-record revision through `POST /v1/company-records/:id/context-reviews`. The request names the action (`approve` or `withdraw`), source classification, provenance, environment, verification method and reference, inclusion reason, validity end, and expected record revision. The server binds the full source digest, current revision, workspace, task, and authenticated owner. This is an **owner attestation** of verification, not an independent evidence check; the original `verificationState` is preserved separately. The receipt is immutable; a later receipt supersedes it by monotonic ordinal. An idempotency request ID rejects changed replays. No production review is inserted by migration or deployment.

For a company-information Ready or launch, Roost reads the latest receipt for each explicitly selected source. A record is included only when the receipt approves that exact digest and revision, belongs to the same task and workspace, is valid now, and matches the deployment environment. Archived, failed or waived, bootstrap, certification, synthetic, fixture, test, runtime-redaction, and legacy-assumption material is excluded by default. A missing, withdrawn, stale, expired, or out-of-scope required source yields an incomplete packet and blocks Ready or launch. The Ready source catalog exposes only eligible records. Review inserts participate in the existing Ready source fence and invalidation triggers. Historical records and receipts remain available to authorized record/history views; ordinary API/MCP search is G9.

The sealed Worker input contains only the selected record fields plus the receipt's provenance, original record source/status/verification state, owner-attested verification, validity, content digest, reviewer, and inclusion reason. Only effective governed decisions enter this information context. The packet revision and signed managed admission bind those bytes through the Worker input seal. The Worker independently rejects missing or expired provenance before native launch. The underlying record text remains untrusted data and cannot grant tools or external writes.

The isolated native proof creates a disposable database, authenticates an owner, checks exclusion before review, appends one review, reaches Ready/claim, reads the exact HTTP context, builds the final Worker bytes, inspects the one included source and one excluded source, sends the bytes to a harmless native stdin sink, and compares its SHA-256 with the signed managed admission. The native sink substitutes for Hermes; it does not prove an actual Hermes/model request, and no paid model is invoked. Production acceptance needs a separately authorized owner review of a real source; no existing production source is auto-adopted.
