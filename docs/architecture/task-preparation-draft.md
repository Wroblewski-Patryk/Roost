# Owner task preparation draft (2026-10-17)

## Authorized boundary

The owner can save incomplete working text in the existing task readiness editor, leave, and resume it after reopening or reloading the page. This is one bounded gate. Saving does not Submit for execution, grant Ready, approve sources, change task links, create a capability grant or queue an execution. The existing Submit validator remains the only path to an accepted Ready contract. A production business-data save is outside this gate's release smoke.

The stored body is the editor's bounded field shape: owner-entered intent, roles, single-task measurement, budgets, acceptance and recovery text, model choice and references by ID/revision. It does not embed CompanyRecord or Procedure bodies, provider credentials, or host configuration. The API refuses detected secrets and protected data in free text; the UI tells the owner to remove them. This is a text preparation surface, not a source library or secret store.

## Data and authority

`task_preparation_drafts` is a new append-only table keyed by request UUID and by `(workspace_id, task_id, version)`. Its composite task foreign key keeps workspace ownership aligned. Each save stores a SHA-256 body digest, actor, editor-context version, execution class, application ID and creation time. An audit Event stores only identifiers and hashes, not the body. The migration creates a table, constraints, indexes and an immutability trigger; it does not update or seed existing business records.

`GET /v1/agent-runtime/tasks/:id/preparation-draft` returns the latest version to the primary workspace owner. `POST` requires the same owner identity, a strict bounded body, a fresh task/editor context version, and the caller's expected draft version. It locks the task row and saves one version and one Event in a serializable transaction. A repeated exact request ID/body returns its prior receipt; reuse with different content fails. A second tab with an old version receives a conflict and cannot overwrite the first. Save refuses a closed task, an accepted Ready pin or an active execution. Referenced workspace records and task-linked application IDs are checked before storage. Stale revisions may remain as working text, visibly marked for review; they are never refreshed into authority by Save.

The owner UI keeps Save draft distinct from Submit. It restores the saved class, application and text on reopen, shows its version and time with an explicit “without Ready” label, and preserves local edits on errors. A conflict requires the owner to inspect the current server version before a new save. If a reply may have been lost, the UI retries the identical request or reads its receipt; it does not silently invent a new request. Task project, goal and assignee changes still use their separate existing action.
