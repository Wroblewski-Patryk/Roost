## Implemented contract in this branch

- Owner-only `POST /v1/process-core/procedures/:id/launch-preview` reads a selected active Project and procedure version. It checks one structured applicability rule (`company`, exact `project`, or a department attached to the project with `owner` or `applicable` relation) and names inputs, the human procedural role, its escalation, the actual Task assignee, each step's executor/output/success/retry/fallback, exact planned task titles, and zero provider/agent effects. A signed five-minute preview is bound to workspace, owner, procedure, project and source digest. Blocked previews carry no launch token. Missing provenance, incomplete controls, external adapters/tools, and unsupported automated or agent steps block launch.
- Owner-only `POST /v1/process-core/procedures/:id/actions/launch` rechecks the preview, workspace owner membership and current source. One serializable transaction writes the immutable run/version/input snapshot, one linked native draft Task per step, audit, and events. Task descriptions contain the needed input field names and stable run ID. Input values remain in the owner-only run view because ordinary workspace members can read Tasks. The UI warns against entering secrets; this flow is for ordinary work inputs, not credential transfer. The route never calls a provider adapter. An exact request ID replays its result; a distinct request ID cannot launch any version in the same procedure family into the same project twice. This is a deliberate first-slice limit; repeatable scheduled runs need a separate reviewed lifecycle contract.
- Owner-only run list/detail projects linked Task statuses, review references and owner-recorded output decisions. `POST /v1/process-core/procedure-runs/:id/steps/:stepId/outcomes` records an append-only accepted output (only after the Task is `done`) or exception with summary and references. The same request ID replays a concurrent committed outcome. A completed Task alone remains `tasks_done_evidence_pending`; all accepted steps become `owner_accepted`, which reports the owner's decision rather than independent verification. Blocked, archived or exception-marked steps remain exceptions. Existing Task detail remains the work surface. Source version/steps/role/project names are pinned in the run even if the catalog later changes.
- The owner workbench provides project and input selection, explicit preview/confirmation, blocker display, and linked run history in PL/EN. No production run is created by deployment or read-only smoke.
