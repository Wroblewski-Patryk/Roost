## Static startup path and attack surface

The following is verified against unchanged exact-pin source, without imports:

1. [cmd_chat](https://github.com/NousResearch/hermes-agent/blob/939e45c91d751fadd94dcd1b873ac3cb44846213/hermes_cli/main.py#L1687)
   calls `run_bootstrap(announce=False)` before forwarding chat arguments.
   [Bootstrap inventory](https://github.com/NousResearch/hermes-agent/blob/939e45c91d751fadd94dcd1b873ac3cb44846213/hermes_cli/free_tier_bootstrap.py#L77)
   calls `resolve_provider("auto", skip_free_tier=True)` independently of the
   explicitly selected chat provider. Later it resolves the auto ladder again.
2. If earlier configured/authenticated providers do not satisfy that ladder,
   [the Bedrock branch](https://github.com/NousResearch/hermes-agent/blob/939e45c91d751fadd94dcd1b873ac3cb44846213/hermes_cli/auth.py#L1512)
   imports `agent.bedrock_adapter`. Explicit provider resolution itself returns
   earlier; the startup auto inventory is the separate reachable path.
3. [Importing that adapter](https://github.com/NousResearch/hermes-agent/blob/939e45c91d751fadd94dcd1b873ac3cb44846213/agent/bedrock_adapter.py#L25)
   calls `ensure("provider.bedrock", prompt=False)`. The
   [allowlist](https://github.com/NousResearch/hermes-agent/blob/939e45c91d751fadd94dcd1b873ac3cb44846213/tools/lazy_deps.py#L39)
   requests boto3==1.42.89. The
   [installer path](https://github.com/NousResearch/hermes-agent/blob/939e45c91d751fadd94dcd1b873ac3cb44846213/tools/lazy_deps.py#L482)
   invokes `uv pip install --compile-bytecode` with that spec, not a frozen lock
   sync, and has pip/ensurepip alternatives. This explains how range-compatible
   but off-lock transitives can appear without a Hermes source change.
4. [The policy gate](https://github.com/NousResearch/hermes-agent/blob/939e45c91d751fadd94dcd1b873ac3cb44846213/tools/lazy_deps.py#L313)
   honors `security.allow_lazy_installs=false`. An unreadable config fails open.
   `HERMES_DISABLE_LAZY_INSTALLS=1` also blocks when no durable lazy target is set;
   `HERMES_LAZY_INSTALL_TARGET` is an exception and must remain absent.

The current Roost v4 preset does not set that security key or disable environment
variable. `PYTHONDONTWRITEBYTECODE=1` prevents ordinary interpreter cache writes;
it does not prohibit a child installer explicitly compiling bytecode. Update
checks being disabled and exact model/tool flags do not disable lazy installers.
This is an installation-boundary gap exposed by B15, not an expansion of B7's
accepted local skills/banner effects. No previous report is retroactively
upgraded to proof that out-of-workspace installation changes never occurred.

AWS packages are optional Bedrock provider dependencies, not required for the
approved openai-codex route. The
[external-secret loader](https://github.com/NousResearch/hermes-agent/blob/939e45c91d751fadd94dcd1b873ac3cb44846213/hermes_cli/env_loader.py#L444)
defers registry imports unless a source is enabled; the bundled registry concerns

Authentication/status paths can also import Bedrock. The analysis establishes
a plausible startup cause, not an observed historical call stack or AWS call.

Presence adds importable cloud SDK code, a query script, network clients and AWS

## Generated bytecode policy

All 4,946 current `.pyc` files map to existing `.py` sources and have the same
CPython 3.13 magic, timestamp-based flags=0, and headers matching source timestamp
and size. The added fingerprint matches `git:HEAD:<pinned commit>`. The
[launch sweep](https://github.com/NousResearch/hermes-agent/blob/939e45c91d751fadd94dcd1b873ac3cb44846213/hermes_cli/main_web_build.py#L26)
creates this fingerprint and may clear checkout caches when it changes. The
[lazy bytecode warmer](https://github.com/NousResearch/hermes-agent/blob/939e45c91d751fadd94dcd1b873ac3cb44846213/tools/lazy_deps.py#L436)
and installer compilation provide other documented generation paths.

Headers do not prove bytecode-body equivalence to source. Reading the pinned
CPython importlib loader confirms that `dont_write_bytecode` governs writes,
not whether an existing validated cache is loaded. Bytecode is derived executable
content, not harmless data that can be broadly ignored. Exact bytes also depend
on interpreter, compile flags, embedded paths and source timestamps; they are
not intrinsically stable across installation/compilation events.

Choose **a separate generated-cache receipt (option b)** outside the immutable
manifest. A future approved maintenance step must generate caches only from
verified sources with the pinned interpreter, without importing the provider,
then bind interpreter/source-set/compiler settings and output hashes. Permit
only bounded `__pycache__/<known-source>.cpython-313[.opt-N].pyc` mappings and the
single known checkout fingerprint; reject orphan bytecode, links/reparse points,
new modules and arbitrary cache files. Header checks are additional diagnostics,
not authorization. Legal regeneration must refresh this receipt through the
controlled maintenance path; it must not require changing immutable source
hashes or create an endless source-drift failure. Unexplained generated changes
remain fail-closed. No cache was deleted or compiled in B15.
