# Internal application operation

## Claim boundary

Gate 5 is in progress. The controls below have source and focused test evidence;
the second application's managed audit, owner adoption, first write, accepted
outcome and native console proof are not yet certified. Each additional
application needs its own audit and context. Whole product, sale readiness,
mobile and later company capabilities remain unverified or deferred.

## Existing application takeover

Reuse the configured requester, accountable manager, executor, independent
verifier/reviewer and releaser competencies. Use the existing published base
procedure plus an application/component extension. Keep the canonical
application lifecycle; do not create another stage engine.

Register each application's own product, technical, inspection and release
context. Identify its canonical repository and clean baseline. Recover source
assumptions and historical evidence separately from current implementation.
Unambiguous defects may form a bounded outcome; contradictory business direction
blocks the affected work for an owner Decision. Dated release records cannot
establish current deployed identity.

Read-only contracts may select whole tracked files and exact line fragments.
At most 32 selections, 200 lines per fragment and 64 KiB of selected content are
permitted. A fragment source is limited to 1 MiB, hashed in full, checked again
after paired native observations, and represented by a separate source digest.
Only selected bytes enter model context. Secret paths, reparse points,
hardlinks, untracked sources, overlaps and whole-file/fragment conflicts are
rejected. Whole-file payload shape and 32 KiB per-file bound remain unchanged.
Native metadata inventory retains at most 32,768 entries per tree; depth,
identity, dirty-file and content limits remain enforced. Large historical
documentation is retained rather than omitted or deleted to fit the observer.
The verifier must retain the auditor's exact selection and evidence binding.
Protected project-state material may be supplied as an explicitly attributed,
dated operator summary; it is never treated as a native model read or current
runtime proof.

After two independent, completed same-application native canaries, propose a
separate `roost-application-takeover-v1` Decision. It binds repository, exact
commit, audit/verifier executions and digests, assumption revisions, bounded
stage, intended user/problem/outcome and limitations. Both product-ready and
sale-ready are false. Only the primary owner may accept it. Current repository,
assumptions, assignments, native receipts and managed approvals are checked at
proposal and acceptance; additive database guards preserve the existing
Decision impact/risk admission. A baseline grants no execution, first-write or
release authority. Those remain separate approvals.

## Portfolio and attention

The application operation projection reads native tasks, current Ready/review
material, canonical Decisions and governed release evidence. Profile stage and
capability percentage are declarations, not completion proof. Show the bounded
stage/source, nearest outcome, accountable role, blocker or actual owner
Decision, and evidence. Gate states are `unmet`, `in_progress`, `met`, `blocked`
or `explicitly_deferred`; product/sale readiness remains unverified.

Console links preserve only validated application, task and Decision IDs.
Opening a record requires a workspace-scoped read-back before the modal or
cockpit opens. A pending Decision is an actual queue record, not a generic
button or a fabricated authorization. History truncation prevents completion
claims and directs the owner to canonical evidence.

## Evidence before completion

Record exact audit/verifier executions, owner baseline and first-write Decisions,
tested coding commit and independent acceptance. Demonstrate approved
continuation and safe waiting through the actual owner queue in the deployed
console. Retain the earlier pilot's evidence and local handoff. Run the
repository checks, affected component checks and required native proof, update
the matrix, then stop at Gate 5. Installation identities and private evidence
stay outside distributed source.

When a scope request returns a content-filter error, reconcile the exact request
and persisted scope before retrying: response projection can fail after commit.
Standalone Basic credentials require an encoded `user:password` pair; ordinary
Basic documentation titles retain their meaning. Authentication fields, known
secrets, split content and encoded credentials remain protected. Verify both
benign catalogue reads and credential rejection when changing this classifier.

Task interviews expose sources pinned by server task context first, then
application-owned assumptions before shared records,
retaining the workspace/application/archive filters and 100-record limit.
Truncation remains explicit; native revision references are never invented.

For bounded pure TypeScript acceptance tests, the installation test manifest
may select `node_typescript_test`: an exact authorized `.test.ts` path, tracked
source paths, and fixed Node 22 strip-types/test arguments. Node, manifest,
package configuration and candidate files are pinned before and after the run.
The Windows Job must close with no remaining processes. Nonempty TAP assertions
must pass; empty, skipped, cancelled or pending tests cannot qualify a candidate.
This configuration does not authorize a write or replace independent review.

Measure the real queued packet and native selections before starting Worker.
The 128 KiB input limit remains enforced. Reserve space for the verifier's
complete prior-auditor report. Execution navigation indexes retain selected
application and pinned source rows; omitted navigation rows have explicit
counts and a canonical digest. Required source bodies and procedure/authority
records remain intact. Secret checks and freshness cover the complete native
response, including omitted index rows. A size measurement issues no launch
proof. Reconcile any earlier pre-model failure and native lock before retrying.
